# Band Site Template

A reusable platform for band websites: **Next.js** (App Router) for the site
and **Sanity** for content, with the Studio embedded at `/studio` so band
members can edit content without touching code.

This repository is a **template**. It currently powers one band, but it is
built to be cloned per client — see [Adding a new band client](#adding-a-new-band-client).

## Stack

- **Next.js 16** (App Router) + **React 19**, TypeScript (strict)
- **Tailwind CSS v4**
- **Sanity v5** CMS, Studio embedded via `next-sanity`
- `@sanity/image-url` for image transforms
- Deploys to **Vercel**

## Project structure

```
app/
  layout.tsx                   Root layout
  page.tsx                     Homepage (Server Component; band smoke test)
  studio/[[...tool]]/page.tsx  Embedded Sanity Studio -> /studio
lib/sanity/
  env.ts                       Validated env vars (single source of truth)
  client.ts                    Public, token-free, published-only client
  image.ts                     urlFor() image URL builder
  queries.ts                   GROQ queries + typed fetch helpers
sanity/
  schemas/                     One file per content type
    band.ts member.ts show.ts release.ts page.ts
    index.ts                   Schema registry
  structure.ts                 Studio desk structure (band as singleton)
sanity.config.ts               Studio + schema config
sanity.cli.ts                  Sanity CLI config (used by typegen)
sanity.types.ts                Generated types — do not edit by hand
docs/superpowers/specs/        Design specs
```

### Architecture rules

- **`lib/sanity/` is the only layer that talks to Sanity.** Server Components
  import query functions from `lib/sanity/queries.ts`. React components never
  call Sanity directly — they receive plain, typed data as props.
- **Types are derived from the schema.** `sanity.types.ts` is generated by
  `npm run typegen`. Every GROQ query is wrapped in `defineQuery` so it gets a
  precise result type. Never hand-edit the generated file.
- **The `band` document is a singleton** — exactly one per deployment,
  enforced in `sanity/structure.ts` and `sanity.config.ts`.
- **Schemas are modular.** Each content type is a self-contained file. Adding
  one is: create the file, register it, regenerate types (see below).

## Running locally

1. Install dependencies:
   ```bash
   npm install
   ```
2. Create `.env.local` from the template and fill in your Sanity values:
   ```bash
   cp .env.example .env.local
   ```
   | Variable | Notes |
   |----------|-------|
   | `NEXT_PUBLIC_SANITY_PROJECT_ID` | From sanity.io/manage. Public. |
   | `NEXT_PUBLIC_SANITY_DATASET` | Usually `production`. Public. |
   | `NEXT_PUBLIC_SANITY_API_VERSION` | API version date. Public. |
   | `SANITY_API_TOKEN` | Server-only. For draft/preview reads. Never expose. |
3. Start the dev server:
   ```bash
   npm run dev
   ```
   - Site: <http://localhost:3000>
   - Studio: <http://localhost:3000/studio>

## The Studio

The Sanity Studio is embedded in this app at **`/studio`** (route:
`app/studio/[[...tool]]/page.tsx`). Band members log in there with a Sanity
account that has been invited to the project — no local setup, no code. In
production it lives at `https://<your-domain>/studio`.

## Adding or changing a content type

1. Create `sanity/schemas/<name>.ts` exporting a `defineType(...)`.
2. Register it in `sanity/schemas/index.ts`.
3. Add any GROQ in `lib/sanity/queries.ts`, wrapped in `defineQuery`.
4. Regenerate types:
   ```bash
   npm run typegen
   ```
   Commit the updated `sanity.types.ts`.

## Adding a new band client

The platform scales by **one Sanity project + one deployment per band**. This
keeps each client's content fully isolated (no cross-tenant leaks) and billed
separately. To onboard a new band:

1. Create a new repo from this one (GitHub "Use this template", or clone).
2. Create a new Sanity project at <https://www.sanity.io/manage> with a
   `production` dataset; invite the band members.
3. Set the new project's env vars in `.env.local` and in Vercel.
4. Deploy to a new Vercel project.

### Tradeoff: keeping clients in sync

Project-per-band means a schema or component change does **not** propagate
automatically — each client repo is independent. Manage this deliberately:

- **Near term:** keep this template as a git `upstream` remote and pull
  template changes into each client repo.
- **Longer term:** extract the shared schema and component library into a
  private npm package that every client repo depends on, so updates ship as a
  version bump.

Pick one before the second client exists — retrofitting it later is painful.

## Deployment (Vercel)

1. Import the repo into Vercel.
2. Add all four environment variables from `.env.local` to the Vercel project.
3. Add the production URL to **CORS origins** in sanity.io/manage so the
   embedded Studio can reach the Sanity API.

Content is cached and revalidated every 60s (`getBand` in
`lib/sanity/queries.ts`). For instant updates, add a Sanity webhook that calls
a revalidation route with `revalidateTag('band')`.

## Out of scope (intentional)

- The `page` schema is authored but not routed yet — add `app/[slug]/page.tsx`
  to render pages.
- Draft/preview mode — `SANITY_API_TOKEN` is wired in `env.ts` ready for a
  server-only preview client.
- The custom React component library that will consume this content.
