# Band Site Template

A reusable platform for band websites: **Next.js** (App Router) for the site
and **Sanity** for content, with the Studio embedded at `/studio` so band
members can edit content without touching code.

This repository is a **template**. Each band client is its own fork with its
own Sanity project and deployment — see [Adding a new band client](#adding-a-new-band-client).

## Stack

- **Next.js 16** (App Router) + **React 19**, TypeScript (strict)
- **Tailwind CSS v4** — theming via CSS custom properties
- **Sanity v5** CMS, Studio embedded via `next-sanity`
- `class-variance-authority` for component variants
- `resend` for the optional email form-delivery path
- Deploys to **Vercel**

## Project structure

```
app/
  layout.tsx                   Root layout — applies theme CSS variables + fonts
  page.tsx                     The composed band homepage (Server Component)
  studio/[[...tool]]/page.tsx  Embedded Sanity Studio -> /studio
components/
  primitives/                  BandLogo, Brand, Button, Heading, Section, SanityImage
  blocks/                      SiteHeader, Hero, About, StatsGrid, MemberGrid,
                               ShowList, MusicGrid, CoverReel, Setlist,
                               BookingForm, MailingListSignup, SiteFooter
  rich-text/                   Portable Text renderer
lib/
  cn.ts                        cn() class-merge helper
  format-date.ts               Pure date formatters
  forms/                       Server actions + pluggable delivery adapters
  sanity/                      env, read client, write client, image, queries
sanity/
  schemas/                     One file per content type + index registry
  structure.ts                 Studio desk structure
scripts/
  demo-content.ts              Demo data for the seed script
  seed.ts                      Populate / clean demo content (npm run seed)
theme/
  fonts.ts                     Per-band font choice
sanity.types.ts                Generated types — do not edit by hand
docs/superpowers/              Design specs and plans (gitignored, local-only)
```

### Architecture rules

- **`lib/sanity/` is the only layer that talks to Sanity.** Server Components
  fetch through `lib/sanity/queries.ts`; blocks never call Sanity — they
  receive plain, typed data as props.
- **Blocks are Server Components.** Interactivity is a small `'use client'`
  leaf inside a block (the forms are the only examples).
- **Types are derived from the schema.** `sanity.types.ts` is generated by
  `npm run typegen`. Never hand-edit it.
- **`band` and `theme` are singletons** — exactly one of each per deployment.
- **Composition is code.** The homepage (`app/page.tsx`) hand-picks which
  blocks appear, their order, and their variants. Customise per band there.

## The component library

Band sites are assembled from `components/blocks/` — a menu of blocks, each
with layout **variants** (e.g. `Hero` has `full-bleed` / `split` /
`typographic`). Three customisation layers:

1. **Theme** — brand colours, logo, corner radius, and density live on the
   `theme` Sanity document and reach components ambiently as CSS variables.
2. **Variant props** — type-safe layout archetypes per block.
3. **`className`** — a per-instance escape hatch on every component.

For anything beyond that, edit the block's source — each fork owns its copy.

## Running locally

1. Install dependencies:
   ```bash
   npm install
   ```
2. Create `.env.local` and fill in your Sanity values:
   ```bash
   cp .env.example .env.local
   ```
   | Variable | Notes |
   |----------|-------|
   | `NEXT_PUBLIC_SANITY_PROJECT_ID` | From sanity.io/manage. Public. |
   | `NEXT_PUBLIC_SANITY_DATASET` | Usually `production`. Public. |
   | `NEXT_PUBLIC_SANITY_API_VERSION` | API version date. Public. |
   | `SANITY_API_TOKEN` | Server-only. Viewer scope for reads; Editor scope to write form submissions or run the seed. |
   | `BOOKING_DELIVERY` | `sanity` or `email` — how form submissions are delivered. |
   | `RESEND_API_KEY` / `RESEND_FROM` / `BOOKING_EMAIL_TO` | Only when `BOOKING_DELIVERY=email`. |
3. Start the dev server:
   ```bash
   npm run dev
   ```
   - Site: <http://localhost:3000>
   - Studio: <http://localhost:3000/studio>

## Demo content

The homepage reads from Sanity, so an empty dataset renders an empty page. To
preview the site with sample content:

```bash
npm run seed         # upload demo images + create demo documents
npm run seed:clean   # remove everything the seed created
```

- The seed needs an **Editor-scoped** `SANITY_API_TOKEN` (the default Viewer
  token cannot write).
- `npm run seed` **overwrites the `theme` and `band` singletons** — only run it
  on a dataset without real content. It is idempotent (safe to re-run).
- `npm run seed:clean` deletes exactly the demo documents and demo image
  assets — use it before entering real content.

## Forms

`BookingForm` and the footer mailing-list signup submit through a Next.js
server action. Delivery is chosen per band by `BOOKING_DELIVERY`:

- `sanity` — writes a `bookingRequest` / `subscriber` document (needs an
  Editor-scoped token).
- `email` — sends via Resend (needs `RESEND_API_KEY`, `RESEND_FROM`,
  `BOOKING_EMAIL_TO`).

Both forms include a honeypot field; validation runs server-side.

## Adding or changing a content type

1. Create `sanity/schemas/<name>.ts` exporting a `defineType(...)`.
2. Register it in `sanity/schemas/index.ts`.
3. Add any GROQ in `lib/sanity/queries.ts`, wrapped in `defineQuery`.
4. Regenerate types and commit `sanity.types.ts`:
   ```bash
   npm run typegen
   ```

## Adding a new band client

The platform scales by **one Sanity project + one deployment per band** — each
client's content stays isolated and is billed separately.

1. Create a new repo from this one (GitHub "Use this template", or clone).
2. Create a new Sanity project at <https://www.sanity.io/manage> with a
   `production` dataset; invite the band members.
3. Set the new project's env vars in `.env.local` and in Vercel.
4. Set the band's typeface in `theme/fonts.ts`.
5. Add content in the Studio — or run `npm run seed` to preview, then
   `npm run seed:clean` before entering real content.
6. Tailor `app/page.tsx`: choose which blocks the homepage composes and their
   variants.
7. Deploy to a new Vercel project.

### Tradeoff: keeping clients in sync

Project-per-band means a template change does **not** propagate automatically.
Manage it deliberately: keep this template as a git `upstream` remote and pull
changes into each client repo, or — once there are several clients — extract
the shared library into a private npm package.

## Deployment (Vercel)

1. Import the repo into Vercel.
2. Add the environment variables from `.env.local` to the Vercel project.
3. Add the production URL to **CORS origins** in sanity.io/manage so the
   embedded Studio can reach the Sanity API.

Content is cached and revalidated (see the `revalidate` settings in
`lib/sanity/queries.ts`). For instant updates, add a Sanity webhook that calls
a revalidation route with the matching `revalidateTag`.

## Out of scope (intentional)

- Per-page routing for `page` documents — add `app/[slug]/page.tsx` to render them.
- Draft/preview mode — `SANITY_API_TOKEN` is wired ready for a preview client.
- A motion/animation system — blocks ship static.
